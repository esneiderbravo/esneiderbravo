# Architecture — esneiderbravo

The structural law of the project. Every change respects these boundaries —
see [`../../LAWS.md`](../../LAWS.md). Use `compass_explore` to navigate the
real code before editing.

- **Overall shape**: Content + CI repository, not a layered application: a single
  rendered README that embeds committed SVG assets and themed remote badge/card
  services, refreshed daily by a GitHub Actions workflow. No runtime services, no
  code layers.
- **Stack**: Markdown + HTML profile README rendered by GitHub, self-hosted metric
  SVGs generated by the lowlighter/metrics GitHub Action, automated by a scheduled
  GitHub Actions workflow (cron). No application runtime, no build step, no package
  manifest.

## Modules / bounded contexts

This repo has no software modules; its "bounded contexts" are the content and
automation areas below, derived from the real directory layout:

| Module | Responsibility |
|--------|----------------|
| Profile README (`README.md`) | The rendered GitHub profile page — hero banner, flagship + selected-work cards, live GitHub metrics section, contact badges |
| Metrics automation (`.github/workflows/metrics.yml`, `metrics.*.svg`) | Daily GitHub Actions job that regenerates the stats and top-languages SVGs via lowlighter/metrics, themed in the teal brand |
| speclaw foundation (`LAWS.md`, `docs/standards/*`, `docs/compass.md`) | The constitution and standards that bind every agent working in this repo |
| Lawbook workflow (`lawbook/`, `ai-specs/skills`, `ai-specs/commands`) | Spec-driven change workflow: draft → build → sync → archive |
| Agent context (`CLAUDE.md`, `AGENTS.md`, `ai-specs/agents`) | Multi-IDE entry points and subagent definitions |


## Layering

This repo has no software layers; its "layering" is a content → asset → CI
pipeline, and the boundaries below are enforced the same way code boundaries
would be:

- **Source of truth is `README.md`.** It embeds committed assets by relative
  path (`./metrics.base.svg`, `./metrics.langs.svg`) and themed remote services
  (shields.io, ghchart, capsule-render, readme-typing-svg, activity-graph).
  Content changes happen here.
- **Generated SVGs are produced only by the metrics workflow.**
  `metrics.base.svg` and `metrics.langs.svg` are outputs — never hand-edited.
  Bot commits that refresh them are marked ` - [Skip GitHub Action]`.
- **The workflow (`metrics.yml`) is the only executable code.** It depends on
  the `METRICS_TOKEN` secret and pinned external Actions; it writes assets back
  to `main`.
- **speclaw docs are the governance layer.** They describe and bind the repo;
  they are not embedded into the rendered profile.


## Cross-boundary rules

- **Content ≠ generated assets.** `README.md` references the SVGs; it never
  reproduces their contents. The SVGs are only ever regenerated by the workflow.
- **The workflow is self-contained.** All automation logic lives in
  `metrics.yml`; it reads only the `METRICS_TOKEN` secret and pinned Actions,
  and writes only the `metrics.*.svg` assets.
- **Governance stays out of the render.** speclaw docs (`LAWS.md`,
  `docs/standards/*`, `ai-specs/`, `lawbook/`) bind the repo but are never
  embedded into the public profile.
- A change that alters the workflow's contract (new asset, new secret, new
  schedule) or restructures the README's sections needs a spec change describing
  it.
